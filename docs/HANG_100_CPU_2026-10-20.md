# Зависание кабины: 100 % CPU, окно не отвечает, кнопки не нажимаются

**Дата разбора:** 20 октября 2026
**Версия:** Star Typing 3.7.0
**Итог:** причина найдена замером, исправлена и проверена на живом запуске.
Коммиты: `49f8c87`, `b76c1bf`, `54bc9c6`, `261b65b`, `4268e37`.

---

## 1. Как это выглядело

- Окно открывалось (экран входа или сразу кабина), но **не отвечало**: нажатия не
  доходили, разделы не переключались, Win+Space не работал.
- Процессор — **100 % одного ядра** (5.0 с CPU за 5 с работы), постоянно, не «рывками».
- Симптом был **не в каждом запуске**: иногда программа работала нормально, иногда
  вставала через 10–20 секунд после старта. Отсюда ощущение «то работает, то нет».
- Правый край шапки и клавиатуры уезжал за границу экрана.

## 2. Причина

**Все 14 экранов лежали в раскладке одновременно** — в одной ячейке сетки, друг на
друге, а переключение делалось через `tkraise()`:

```python
for scr in self.screens.values():
    scr.grid(row=0, column=0, sticky="nsew")   # все экраны сразу
...
scr.tkraise()                                  # «показать» нужный
```

Tk на Windows **перерисовывает и перекрытые окна** — он не умеет пропускать
невидимое. Значит, каждый такт рисовались все экраны, а внутри невидимых лежат
большие текстовые поля:

- книга в «Скорочтении» (~103 000 слов, 3 377 слов уже прочитано),
- лента переписки с Орионом,
- тексты вкладки «Английский».

Профиль главного потока (`py-spy record --native`) показал ровно это — измерение и
отрисовку символов внутри обработки событий Tcl:

```
Tcl_DoOneEvent -> Tcl_ServiceEvent -> TkTextXviewCmd -> Tk_MeasureChars -> Tk_DrawCharsInContext
Tcl_DoOneEvent -> Tcl_ServiceEvent -> TkBTreeNumLines (x5)
```

`TkTextXviewCmd` — команда текстового виджета (`xview`/`yview`), `TkBTreeNumLines` —
обход дерева строк документа, `Tk_MeasureChars`/`Tk_DrawCharsInContext` — измерение и
рисование текста. То есть процессор жгло не приложение, а **отрисовка больших текстов
на невидимых экранах**.

Вторая, связанная причина: контейнер экранов сообщал окну ширину **самого широкого**
экрана (2601 px при окне 1920 px). Из-за этого окно считало себя шире экрана, а шапка
и клавиатура вылезали за правый край.

Почему «то работает, то нет»: зависание запускалось, когда в невидимых экранах
появлялся тяжёлый текст (загружалась книга, подтягивалась лента) — то есть зависело от
состояния данных, а не от кода запуска.

## 3. Что причиной НЕ было (проверено и отброшено)

| Гипотеза | Как проверяли | Результат |
|---|---|---|
| Вход через экран логина и «второй корень Tk» | запуск без экрана входа | зависало одинаково — не причина |
| Шторм событий `<Configure>` в шапке | счётчик перерисовок по виджетам | 2–5 вызовов в секунду — норма |
| Звёзды/клавиатура/приборы (анимация 30 к/с) | отключение по одному узлу, 8 запусков | все варианты дали норму — не причина |
| Утечка таймеров `after()` | счётчик висящих таймеров | стабильно 11–14 — не причина |
| «Замирания» в журнале | оказалось: пульс главного потока выключался через 25 с | ложная тревога, исправлено |

## 4. Что исправлено

### 4.1. В раскладке остаётся один экран (`stamina/cockpit.py`)

Новый метод `_only_screen(name)`: нужный экран ставится в сетку, остальные убираются
через `grid_remove()`. Вызывается из `show()` и сразу после построения кабины.

Важная деталь, из-за которой первая версия правки **не срабатывала** при обычном
запуске: признак «экран в раскладке» брался через `winfo_ismapped()`, а на старте окно
ещё не отрисовано, и этот признак равен нулю у всех экранов. Правильный признак —
`winfo_manager() == "grid"`.

### 4.2. Контейнер экранов не растягивает окно

```python
self.content.grid_propagate(False)
```

Теперь окно не подстраивается под самый широкий экран.

### 4.3. Окно не выходит за экран (`_apply_geometry`, `_fit_to_content`)

Сохранённая раскладка принимается, только если окно целиком влезает в экран; иначе
окно ставится по экрану с запасом.

### 4.4. Диагностика на будущее (`stamina/app.py`)

- **пульс главного потока** больше не выключается через 25 с — журнал замираний снова
  честный (раньше он писал «замирания» с растущим временем просто потому, что пульс
  замолчал);
- **сторож петель раскладки**: считает `<Configure>` по виджетам и, если виджет
  зациклился (300 событий за секунду), снимает с него обработчик и пишет имя в журнал;
- **журнал долгих обратных вызовов**: пишет в журнал вызовы, которые держат главный
  поток дольше 0.2 с;
- **снимки состояния** первых 12 секунд дополнительно пишут требуемую и фактическую
  ширину строк и экранов — сразу видно, что не влезает.

## 5. Проверка (замеры `process_time`, 100 % = 5.0 с за 5 с)

| Сценарий | До | После |
|---|---|---|
| Прямой запуск кабины | 4.92–4.98 за 5 с (**100 %**) | 0.61 / 0.64 / 0.30 за 5 с |
| Обычный путь: экран входа → кабина | 100 % | 1.50 за 5 с (~30 %) |
| Переключение 8 разделов подряд | окно вставало | 0.62–1.39 за 3 с, ошибок нет, видим всегда один экран |

Норма для этой программы — 12–30 % одного ядра (анимация звёзд 30 к/с и приборы).

## 6. Правила, чтобы не повторилось

1. **Не держать в раскладке невидимые экраны.** Один экран — одна ячейка. Все экраны
   сразу — только если внутри нет тяжёлых текстов.
2. **Не вызывать `update_idletasks()` внутри обработчиков геометрии** — он прокачивает
   очередь событий и превращает одно событие в шторм.
3. **Рисовать один раз на такт.** Для канвасов есть `_LazyDraw` в `stamina/hud.py`:
   несколько `<Configure>` подряд превращаются в одну отрисовку.
4. **Сравнивать состояние перед перерисовкой.** Если размер, текст и состояние не
   изменились — не рисовать.
5. **Любую правку производительности подтверждать замером**, а не «на глаз»:
   `process_time` внутри процесса и `py-spy record --native` снаружи.

Снять профиль висящего процесса (нужен `py-spy`):

```powershell

```

Смотреть в конце строк — там самые «горячие» функции.
