## 2. Что уже работает и чего нет

### Работает

- Десктоп: печать, миссии, английский, скорочтение, PDF, библиотека, скины, экипаж, статистика,
  автообновления из Releases. Офлайн — полностью.
- Веб: те же зоны, PWA, радио, игры, Орион со скриптами и голосом, Docker-ярлык, проверка обновлений.
- Единый стандарт хоткеев на обоих клиентах (18.10.2026).
- Веб-навигация без мыши: `Tab`/`Shift+Tab`/`Esc`, стрелки по HUD-кнопкам, `Ctrl+Home`/`Ctrl+End`.
- i18n: ru/uk/en/de на десктопе; веб — свой `setup.ts` + `public/locales`.

### Не работает / не начато

- Always-on хостинг, домен, TLS, бэкапы, мониторинг.
- Онлайн-аккаунт, привязка локального пилота к нему.
- Лидерборд и античит.
- Форма обратной связи «радиограммы».
- Всё остальное из I-001…I-010 (эфир, флоты, ангар, кубки, карта, Орион Online, учитель, рукописи).

## 3. Архитектура и карта репозиториев

### 3.1. Десктоп (`D:\My_New_Stamina`)

```text
stamina/
  cockpit.py        главное окно, шапка, зоны, глобальные хоткеи (_chrome_hotkey)
  bridge.py         мостик: набор, пауза, отчёт
  screens.py        экраны настроек и простоя
  comm.py           «ЭФИР»: лента сообщений экипажа — слой данных (прототип, без Tk)
  comm_screen.py    «ЭФИР»: экран раздела (лента, ввод, непрочитанное)
  keynav.py         навигация без мыши (Tab, стрелки, Esc/Del, хоткеи с кнопок)
  page_help.py      справка F1, GLOBAL_KEYS, HOTKEYS по зонам
  missions.py       миссии, генерация упражнений, ремонт
  english/          английская зона
  speedread/        скорочтение и книжная читалка (book_reader.py)
  lounge/           отдых
  radio/            радио
  i18n/             ru.json, uk.json, en.json, de.json
  themes/           скины (в т.ч. old_england.json)
  idle/             слайдшоу простоя
  hud.py            HudButton и элементы HUD
tests/              unittest
tools/i18n_check.py проверка ключей/переводов
```

**Точка входа:** `stamina/app.py` / `stamina/cockpit.py`.  
**Данные:** `%APPDATA%\Stamina`; пилоты — `pilots\<id>\`.

## 4. Зафиксированные решения

| ID | Решение | Почему |
| --- | --- | --- |
| **D1** | Хоткеи: `Home` Орион, `PgUp` слайды, `PgDn` экран, `Esc`/`Del` пауза. Без `Ctrl`/`Alt`/`Shift` | Chrome резервирует `Ctrl+PgUp/PgDn`; локальные клавиши читалок не перебиваем |
| **D2** | Хостинг: **один VPS в EU** (Hetzner CX22/CX23 или аналог) + `docker compose` + Caddy + бэкапы | Убирает CORS, `SameSite=None`, патч `fetch`; стек = локальному |
| **D3** | **API — ядро**; веб — первый онлайн-клиент; десктоп подключается тем же API позже | Не строить два клиента сразу, но не закрывать десктопу путь |
| **D4** | Авторизация: cookie (httpOnly) для веба, Bearer-токен для десктопа; сервер принимает оба | Один контракт, два транспорта |
| **D5** | **Сначала бесплатная ценность**, деньги — вручную (донат-ссылка + код спонсора) | Донат без аудитории = 0 ₴ + юрработа |
| **D6** | Десктоп остаётся **офлайн-first**; онлайн — необязательная надстройка | Офлайн — преимущество, его нельзя ломать |
| **D7** | Привязка локального пилота к аккаунту — **по желанию, без автопереноса** | Прогресс священен; авто-миграция = риск и поддержка |
| **D8** | Лидерборд: сначала **недельный рейтинг + звание в нике**, чат — позже | Лидерборд не требует realtime и модерации |
| **D9** | Античит: серверный текст + nonce + поток keystroke-таймингов + отсев невозможных WPM + ручная очередь | Итогового WPM недостаточно |
| **D10** | I-002: `home_fleet` — ярлык/фильтр на существующих скинах, **отдельно** от `active_skin` | Ноль нового арта; нет конфликта с ангаром |
| **D11** | I-005: сначала **асинхронный кубок на 24 ч**; топ-3 → trial premium, топ сезона → trophy-skin | Проще серверно; рейтинг не продаётся |
| **D12** | I-009: **BYOK первым**, только личный диалог, квота реплик, память-саммари | Нулевая себестоимость; self-host GPU не влезает в бюджет |
| **D13** | I-006 (кабинет учителя) — **отдельный продукт/трек**, не этап общего MVP | GDPR, согласие родителей, лицензии учебников |
| **D14** | I-007: каталог + модерация + оценки; **продажа только внешними ссылками**; takedown + «пожаловаться» | Checkout внутри = юридический риск |
| **D15** | Метрики — только серверные агрегаты **без PII**; никакой сторонней слежки | В духе продукта и приватности |

**Что не продаём:** место в рейтинге, скорость, «читерские» преимущества. Платим за глубину:
обшивка, разум, поддержка.

## 6. Границы Online MVP и парковка

### Входит в Online MVP (E0–E3)

- сервер always-on: VPS, домен, TLS, бэкапы, мониторинг;
- онлайн-аккаунт и привязка локального пилота;
- недельный лидерборд + античит-минимум;
- радиограммы (обратная связь);
- веб — первый клиент; десктоп — привязка пилота и чтение лидерборда.

### Не входит (парковка, E4+)

- эфир/чат, presence;
- флоты/космодромы, ангар premium-скинов;
- кубки, карта секторов, анимация взлёта;
- Орион Online (LLM);
- кабинет учителя;
- верфь рукописей;
- биллинг и подписки.

> **Исключение (решение владельца, 18.10.2026).** В **десктопе** собран прототип раздела «ЭФИР»:
> локальная лента сообщений экипажа одного компьютера (`stamina/comm.py`, `comm_screen.py`,
> `comm_hook.py`, тесты `tests/test_comm.py`). Это проверка механизма «пилоты переписываются» и
> **фундамент будущего онлайн-чата**: слой данных повторяет будущее серверное API, чтобы экран не
> переписывать. Десктоп остаётся прототипом-песочницей (D6), онлайн-эфир, presence и модерация —
> по-прежнему в парковке E4-02.

**Правило:** этапы E4+ не начинаются, пока Online MVP не наберёт метрики из раздела 11.

### 8.1. Волны

```text
Волна 0  (1 агент + владелец)   E0: решения, контракт, спеки
   │
   ├── Волна 1 (4 параллельно)
   │     infra:    E1-01…E1-07
   │     backend:  E1-08…E1-10
   │     web:      E1-11 (на mock)
   │     desktop:  E1-12…E1-13 (на mock)
   │     reviewer: E0-08 + план проверок
   │
   ├── Волна 2 (3–4 параллельно)
   │     backend:  E2-01…E2-05, E3-01…E3-02
   │     web:      E2-06, E3-03
   │     desktop:  E2-07, E3-04
   │     reviewer: E2-08…E2-09
   │
   ├── Волна 3 (интеграция, 1–2 агента)
   │     E1-14, E2-06/E2-07 на живом API, E3-05
   │
   └── Волна 4 (релиз)
         бэкап, smoke, метрики, CHANGELOG
```

**Правила волн:**

- Внутри волны агенты не зависят друг от друга **только если** контракт заморожен.
- Клиенты (веб/десктоп) начинают на **mock-сервере**, а не ждут backend.
- Интеграция — отдельная волна, не «по ходу».
- Максимум 4 implementer-агента + 1 reviewer. Больше — конфликты и шум.

### 8.2. Карта владения файлами

| Роль | Владеет | Не трогает |
| --- | --- | --- |
| **Infra** | `web_star_typing/docker-compose*.yml`, `Caddyfile`, `deploy/**`, `.github/workflows/**`, `.env.example` | код приложения |
| **Backend** | `web_star_typing/backend/**` (кроме `Dockerfile` без согласования) | `frontend/**`, `stamina/**` |
| **Web** | `web_star_typing/frontend/**`, `web_star_typing/packages/**` | `backend/**`, `stamina/**` |
| **Desktop** | `stamina/**`, `tests/**`, `tools/**` | `web_star_typing/**` |
| **Docs** | `docs/**`, `README.md` (кроме CHANGELOG в релизе) | код |
| **Reviewer** | `docs/reviews/**` (только отчёты) | всё остальное |

**Жёсткие правила:**

1. Один файл — один владелец в рамках волны. Если нужна правка чужого файла — issue/PR-комментарий.
2. `web_star_typing/` — отдельный git. Веб-агент **никогда** не коммитит из корня; десктоп-агент —
   из `web_star_typing/`.
3. `stamina/i18n/*.json` — только один агент (desktop), иначе конфликты в 4 файлах.
4. `docker-compose.yml` — только infra; backend предлагает изменения, не правит сам.
5. `CHANGELOG.md` — только orchestrator в релизной волне.

### 8.3. Контракты между агентами

- **OpenAPI v0** (E0-06) — единственный источник правды по эндпоинтам.
- Изменение контракта = новая версия + уведомление всех агентов + обновление mock.
- Mock-сервер обязателен: клиенты не ждут backend.
- Общие типы — генерировать из OpenAPI (если возможно), иначе синхронизировать вручную и проверять тестом.
- `.env.example` — infra; backend добавляет переменные только через PR в infra-файл.

### 8.4. Git-протокол

- Ветка на задачу: `task/E1-09-auth-endpoints`.
- Один PR = одна задача (или 2–3 мелкие одного эпика).
- Conventional commits: `feat(api): ...`, `fix(web): ...`, `docs: ...`.
- Автор не мержит свой PR. Мержит orchestrator после PASS ревьюера.
- Перед PR: локальные тесты + `i18n_check` (если затронут UI-текст).
- В PR обязательно: что сделано, как проверено, риски, скрин (для UI).

## 9. Ревьюер-агент

### 9.1. Роль

**Gatekeeper** — отдельный агент, который проверяет работу группы и имеет право блокировать merge.
Он **не автор** и **не мержит**. Его задача — не переписать код, а не пустить регресс, дыру и мусор.

### 9.2. Как назначить

| Параметр | Значение |
| --- | --- |
| Когда | в волне 0, до старта implementer-агентов |
| Формат | отдельная постоянная сессия/сабагент, желательно **другая модель**, чем у авторов |
| Доступ | read-only по коду + право запускать тесты; писать только в `docs/reviews/**` |
| Срок жизни | весь Online MVP, не «на один PR» |
| Подчинение | orchestrator; по security/privacy — право вето |
| Загрузка | 1 ревьюер на 4 implementer-агента |

### 9.3. Входы и выходы

**Вход на каждое ревью:**

1. ID задачи и её критерий готовности.
2. `git diff main...task/...` (или список файлов).
3. Команды проверки и **самостоятельно полученный** вывод тестов.
4. Заметки автора о рисках и компромиссах.
5. Скриншот/запись для UI-изменений.

**Выход:**

```markdown
## Вердикт: PASS | PASS WITH NITS | CHANGES REQUIRED | BLOCKED

### Блокирующие (P0)
- file:line — что не так — что требуется

### Важные (P1)
- ...

### Мелочи (P2)
- ...

### Проверено
- [ ] критерий готовности
- [ ] тесты запущены вручную
- [ ] i18n
- [ ] безопасность/приватность
- [ ] офлайн/кросс-платформа
- [ ] нет мусора/секретов/PII

### Что я не проверял
- ...
```

### 9.4. Полномочия и эскалация

- **P0** (безопасность, потеря данных, приватность, падение прода) — блокирует merge безусловно.
- **P1** — блокирует merge, если не согласован перенос.
- **P2** — не блокирует, но заносится в задачу.
- Два разногласия автора и ревьюера → решает orchestrator.
- Security/privacy → голос ревьюера сильнее.
- Продуктовые вопросы → владелец.

### 9.5. Анти-паттерны ревьюера

- Переписывать код вместо замечаний.
- Верить выводу тестов автора, не запуская самому.
- Ревьюить всю репу вместо diff + контекста.
- «LGTM» без чеклиста.
- Блокировать из-за вкусовщины без P0/P1-обоснования.
- Молча пропускать отсутствие тестов, i18n, доков.

## 10. Definition of Done (чеклист ревьюера)

Задача закрыта, только если:

- [ ] Все критерии готовности выполнены.
- [ ] Новые тесты есть; все тесты проходят; **нет новых падений**.
- [ ] i18n: ключи добавлены в ru/uk/en/de; `python tools/i18n_check.py` — exit 0.
- [ ] Веб-строки — через `t()`, десктопные — через `_t()`; литералов в UI нет.
- [ ] Только дизайн-токены; хардкод цветов/размеров отсутствует.
- [ ] Десктоп работает на Windows и Linux (хотя бы smoke).
- [ ] Офлайн-десктоп не сломан; сетевые вызовы с таймаутами.
- [ ] Безопасность: секреты не в git, вход валидируется, лимиты есть, авторизация проверена.
- [ ] Приватность: в логах нет PII; для таймингов есть consent; удаление данных работает.
- [ ] Документация: README/справка/CHANGELOG, если изменение видно пользователю.
- [ ] Нет мусора, временных файлов, чужих данных, `.db`/`.env` в коммите.
- [ ] Коммиты атомарные, сообщение по конвенции.
- [ ] Производительность: нет очевидных N+1, лишних ререндеров, раздувания бандла.

## 11. Метрики и kill-criteria

### Цели Online MVP (первые 6 недель после запуска)

| Метрика | Цель | Как считаем |
| --- | --- | --- |
| Онлайн-аккаунты | ≥ 30 | сервер |
| Привязали локального пилота | ≥ 50 % от аккаунтов | сервер |
| Недельные забеги в лидерборде | ≥ 20 | сервер |
| Радиограммы | ≥ 10 / неделю | сервер |
| Week-2 retention | ≥ 30 % | сервер, агрегат |
| Успешные сабмиты | ≥ 95 % | сервер |
| API p95 | < 300 мс | мониторинг |
| Uptime | ≥ 99,5 % | мониторинг |

### Kill-criteria

- Через 6 недель **< 10** недельно-активных → не расширять фичи, вернуться к ценности.
- **0–2** радиограммы за 3 недели → проблема в продукте/канале, не в форме.
- Хостинг + LLM выше бюджета при отсутствии роста → заморозить платный контур.
- Модерация чата некому вести → чат не запускать.

### Что не делаем ради метрик

- Не покупаем рейтинг и не продаём место в таблице.
- Не добавляем стороннюю аналитику и трекеры.
- Не храним PII сверх необходимого.

## 13. Конвенции и грабли

### Обязательные конвенции

1. **UI-строки** — только `t()` / `_t()`; ключ i18n — **русская исходная строка**.
2. При смене текста менять **ключ во всех четырёх** файлах, а не только значение.
3. **i18n JSON** — CRLF + финальный перевод строки; править текстовой заменой, не `json.dump`
   (иначе дифф всего файла).
4. **Скины/цвета** — только токены, без хардкода.
5. **Кроссплатформенность** — Windows и Linux.
6. **Вложенные репозитории** — `web_star_typing/` отдельный git; не смешивать коммиты.
7. **Никакого мусора** — `_tmp_*`, `_missing_*`, `.db`, `.env`, личные данные не коммитить.
8. **Данные пользователя** — не удалять без бэкапа.
9. **Тесты** — новые фичи с тестами; не «починить» чужие падения заодно.
10. **Хоткеи** — не перебивать локальные клавиши читалок/списков/полей ввода.

### Команды проверки

```powershell
# десктоп
python tools/i18n_check.py
python -m unittest tests.test_web_nav_port
# (полный прогон — по мере наличия тестов)

# веб
cd web_star_typing\frontend
npm test -- --run
npm run build

# бэкенд
cd web_star_typing\backend
pytest
```

### Известные грабли

| Грабля | Что делать |
| --- | --- |
| Windows-консоль cp1251 не печатает кириллицу/символы | писать вывод в файл или читать через `read`/`grep` |
| `bind_all` + локальный обработчик = двойное срабатывание | возвращать `break`, ставить guard по зоне |
| 4 падения в `skinStarshipIntact.test.ts` | прежняя проблема jsdom/localStorage; не связана с задачей; чинить отдельно |
| Ключ i18n не найден после смены текста | обновить ключ, а не только значение, во всех 4 файлах |
